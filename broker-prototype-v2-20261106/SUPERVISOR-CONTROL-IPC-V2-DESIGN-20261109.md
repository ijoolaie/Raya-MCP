# Supervisor–Worker authenticated control IPC v2
Date: 2026-11-09
Status: design only; no pipe, service, identity, ACL, or Production changes

## Purpose and boundary

Define the minimum local control channel between the independent Supervisor and its one Worker. This channel is not the filesystem request protocol and must never carry filesystem paths, file handles, credentials, or arbitrary process commands. It is limited to lifecycle and health control. The existing `process-supervisor-v2` Job Object remains the containment boundary; IPC failure must never detach or unsupervise the Worker.

## Transport and framing

- Use one local, message-mode named pipe instance per Worker generation. The pipe name is generated by the Supervisor from a cryptographically random generation identifier; it is not a stable global rendezvous name.
- Create the pipe with `PIPE_REJECT_REMOTE_CLIENTS`, a protected DACL granting access only to the dedicated service SID and SYSTEM/Administrators for recovery. The actual service SID and token model must be validated before implementation; this document does not authorize provisioning them.
- Reuse the already-tested RY2R v2 fixed frame envelope: magic `RY2R`, version 2, fixed 16-byte header, request/response frame types, nonzero big-endian request ID, bounded payload length (maximum 65,536), and zero reserved field. Reject malformed headers, unknown message codes, duplicate/out-of-order request IDs, oversized payloads, and partial/ambiguous frames. Never add a path-based or alternate transport fallback.
- Control payloads use fixed-width fields and explicit byte order. No native C struct is copied directly onto the wire. Each message has an exact length; trailing bytes are rejected.
- One connection is bound to one Worker generation. Disconnect, timeout, malformed input, failed authentication, or uncertain I/O invalidates that connection. A reconnect is a new handshake with a fresh generation and nonce; never attach to an unknown pre-existing process.

## Peer authentication (both directions)

### Supervisor authenticates Worker

1. Supervisor creates the Worker suspended, assigns it to its private kill-on-close Job, verifies membership, records the process HANDLE/PID, then resumes it.
2. Worker connects only to the generation-specific local pipe name passed through a narrowly defined non-secret startup argument or inherited allowlisted channel. Do not put secrets in command lines.
3. Supervisor obtains the connected client PID from the pipe using the OS peer-PID API. It must equal the PID associated with the already-owned process HANDLE; do not trust a PID supplied in a message.
4. Supervisor impersonates the pipe client only long enough to query TokenUser, TokenSessionId, and the expected service SID membership/state. It always reverts before any other operation, including every error path. Verify the effective token against the configured dedicated service identity; a matching account name alone is insufficient.
5. Supervisor verifies the peer process is still the exact child it launched (owned process HANDLE remains authoritative), is still in the expected Job, and has not exited. Any mismatch closes the session and triggers the configured fail-closed lifecycle response.

### Worker authenticates Supervisor

1. Worker obtains the server PID from the connected pipe using the OS peer-PID API. It opens that process with the minimum query rights and verifies its process token (TokenUser, TokenSessionId, and expected service SID) against the configured Supervisor identity. It does not accept a PID asserted only in a pipe message or command-line field.
2. Worker rejects an unexpected, interactive-user, LocalSystem, or remote peer. The pipe DACL and OS-reported peer token are independent gates; PID equality alone is not authentication.
3. Worker completes a fresh nonce-binding exchange for this pipe instance and generation. The nonce is generated by the OS cryptographic RNG and is single-use. It prevents accidental stale-session/replay confusion but is not a cryptographic authenticator or substitute for OS peer identity and ACL checks.
4. The Supervisor must not expose its Job HANDLE or any handle with equivalent authority to the Worker. Handle inheritance remains disabled; any future handle transfer requires an explicit audited allowlist and duplication direction.

## Handshake and message state machine

The RY2R frame type distinguishes request/response; the first request/response payload opcode is one of:

- `HELLO`: protocol minor version, Worker build identifier, generation identifier, and fresh Worker nonce. No PID or identity field in this message is authoritative.
- `CHALLENGE`: echoed generation identifier and fresh Supervisor nonce.
- `AUTH_BINDING`: echoes the generation and both nonces in a fixed transcript layout. This is freshness/session binding only, not proof of secret possession. Authentication is provided by the independent Windows pipe ACL, peer PID, and peer token checks; no shared static secret is embedded in either binary.
- `READY`: confirms both sides completed OS identity checks and challenge binding. No operational message is accepted before READY.
- `PING` / `PONG`: liveness only; bounded cadence and deadline are configured by the Supervisor.
- `STOP`: graceful stop request with a bounded drain deadline and reason code from a fixed enum.
- `STOPPED`: Worker confirms it has stopped admitting work and drained/reaped its owned operations. It is not proof of process exit; Supervisor still waits on the process HANDLE.
- `FATAL`: fixed diagnostic code and bounded non-secret detail code. No free-form command, path, token, or arbitrary data.

Allowed transitions:

`DISCONNECTED -> CONNECTED_UNAUTHENTICATED -> AUTHENTICATING -> READY -> STOP_REQUESTED -> STOPPED -> PROCESS_EXITED -> CLOSED`.

Any authentication, framing, request-ID, deadline, peer-liveness, or I/O uncertainty transitions to `DEGRADED`. From DEGRADED, the Supervisor stops accepting control messages, retains all owned handles, and applies only the configured bounded policy: wait for process exit, retry authenticated graceful stop only if the connection state is proven valid, or terminate the entire assigned Job after the drain deadline. Never terminate a thread. Never close Job/process handles until process exit is positively observed and collected.

## Deadlines, ordering, and resource limits

- One outstanding lifecycle request at a time; monotonically increasing nonzero request IDs within a connection. Duplicate, stale, skipped where ordering matters, or mismatched response IDs are rejected.
- Handshake deadline, heartbeat interval, heartbeat miss threshold, graceful-stop drain deadline, and maximum frame size are compile-time/configuration-bounded. No unbounded waits or peer-controlled timeout values.
- Bound pipe instances, outstanding operations, buffers, and diagnostic payloads. No unbounded queue growth. On disconnect during a frame, discard the connection and frame state; never splice bytes from a new connection into an old frame.
- Do not log nonce values, tokens, command lines, or arbitrary peer payloads. Diagnostics use fixed enums, PID from the owned process record, and timestamps.

## Failure policy

- Pipe creation/ACL failure: do not launch Worker.
- Worker launch/Job assignment/identity verification failure: fail closed; never start an unsupervised Worker.
- Authentication failure or peer PID/token mismatch: reject connection; do not downgrade to PID-only or SID-only authentication.
- Partial frame, malformed frame, duplicate request, timeout, cancellation uncertainty, or disconnect: mark channel DEGRADED and retain process/Job ownership.
- Graceful STOP timeout: after the configured drain deadline, terminate the whole Job; wait for positive process exit before closing handles.
- Supervisor crash: kernel closes the last Job handle and kill-on-close contains the Worker; restart creates a new Job, generation, pipe, and Worker. Never reattach to an old Worker.
- `STOPPED` or pipe disconnect alone never authorizes handle release.

## Test-only implementation sequence

1. Unit-test payload codecs and state transitions without OS handles: exact lengths, endian values, unknown opcodes, duplicate IDs, replayed nonce, wrong generation, out-of-order messages, overflow, and all illegal transitions.
2. Add a disposable native named-pipe harness with two inert test processes. Test local-only pipe behavior, message boundaries, partial transfers, disconnect at every frame boundary, slow peer deadlines, duplicate/out-of-order IDs, and cleanup.
3. Add peer PID and token/SID/session verification tests using disposable test identities only after an approved identity-provisioning plan exists. Until then, identity acceptance is NOT TESTED.
4. Add Job membership and process-HANDLE cross-checks to the live pipe harness. Verify that IPC disconnect does not release the Job and that whole-Job termination plus positive process wait is required for close.
5. Add supervisor crash/restart tests in an isolated disposable environment. Verify old Worker death, no stale pipe reuse, fresh generation, and no orphaned child processes.
6. Only after the above, consider wiring this channel to the integrated Worker. Do not add filesystem verbs or connect it to the production MCP server in this phase.

## Explicit non-goals and blockers

- This design does not implement or authorize a Windows service, service SID provisioning, ACL changes, production executable, restart service configuration, or Production integration.
- OS identity verification APIs, exact service-token requirements, pipe DACL SDDL, and launch-context binding need a separately reviewed implementation plan before coding.
- No shared static secret is embedded in either binary. If cryptographic channel authentication beyond OS token/PID/ACL checks is later required, it needs a separate key lifecycle design; do not improvise one in the protocol parser.
- No filesystem operations, user payloads, path arguments, shell commands, or arbitrary RPC are permitted on this control channel.
